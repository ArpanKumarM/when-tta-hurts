# Statistical Analysis Plan

**Status: baseline matrix (blocks A/B/C) APPROVED as of Phase 2B.1 — see
`docs/phase2b_protocol.md`. The confirmatory/exploratory classification
below is consistent with, and referenced by, that document's secondary-
analysis freeze (sec.3). Validation-Gated TTA remains draft/not approved.**

## Design

- **Seeds:** 3 final random seeds per confirmatory cell (weight init +
  data-loader shuffling + augmentation sampling). 1-seed pilots are
  exploratory only and are never reported as confirmatory results.
- **Pairing:** Clean and TTA predictions are evaluated on the *same* test
  samples from the *same* trained model, so comparisons are paired, not
  independent-groups. All primary tests must use paired methods.

## Primary analysis (per confirmatory cell: dataset × model × normalization
× resolution × condition)

- **Delta accuracy:** paired bootstrap (resample test samples with
  replacement, ≥ 10,000 resamples) to get a 95% CI on TTA accuracy − clean
  accuracy, per seed, then summarized (e.g. median + range) across the 3
  seeds. Report the CI, not just the point estimate.
- **McNemar's test** on the clean-correct/incorrect vs. TTA-correct/incorrect
  2×2 contingency table, per seed, since this is exactly the paired
  binary-outcome case McNemar is designed for. Report exact or
  continuity-corrected McNemar depending on cell counts.
- **Effect sizes**, not just p-values: report the raw delta-accuracy
  magnitude, the harm rate and rescue rate (already effect-size-like
  quantities), and standardized differences for calibration metrics (NLL,
  ECE, Brier) where meaningful.

## Multiple comparisons

Four pre-registered hypotheses (H1–H4), each tested across multiple
dataset/resolution/model cells. Plan:

- Within each hypothesis's confirmatory test set, apply Benjamini-Hochberg
  FDR correction across the cells tested for that hypothesis (rather than a
  single Bonferroni across all cells and all hypotheses, which would be
  needlessly conservative given the hypotheses ask different questions).
- Report both corrected and uncorrected p-values in result tables so
  readers can see the correction's effect.
- Any test not part of the pre-registered set (i.e., anything from
  exploratory analysis) is clearly labeled exploratory and excluded from
  the corrected confirmatory family.

## Confirmatory vs. exploratory separation

- **Confirmatory:** only the cells in the frozen (`status: approved`)
  `configs/experiment_matrix.yaml` confirmatory matrix, evaluated once per
  seed, on the official test set, using the frozen validation-gated TTA
  config. Reported in the main results tables.
- **Exploratory:** anything else — pilot-stage findings, post-hoc cuts of
  the data, additional normalization variants tried outside the frozen
  matrix, alternative divergence metrics explored after seeing pilot
  results. Reported in a clearly separate section, explicitly labeled
  exploratory, with a note that it has not been corrected for multiple
  comparisons or validated on held-out data and should not be treated as
  confirmatory evidence.

## Every pre-registered primary configuration is reported

Even null or negative results for pre-registered cells are reported — no
selective reporting of only the cells that "worked."

## Test firewall enforcement in the analysis

- No statistical test result computed on the test set may feed back into
  changing the validation-gating algorithm, transform pool, or
  hyperparameters. If exploratory test-set analysis suggests an improvement,
  that improvement must be re-validated as a new frozen configuration
  evaluated on a fresh test pass (or explicitly flagged as no longer a
  held-out evaluation), never silently substituted into the confirmatory
  results.
- Every test-set evaluation is logged in `artifacts/ledger.csv` (corrected
  path — matches the actual implementation, `src/when_tta_hurts/ledger.py`;
  append-only) regardless of outcome, so the number of test-set "looks" is
  auditable.

## Reporting requirements

- All headline numbers in any document must be generated by a script reading
  `results/` — never hand-typed.
- Report seed-level variance (e.g. min/median/max or mean ± SD across the 3
  seeds), not just an aggregate mean that hides run-to-run variability.
